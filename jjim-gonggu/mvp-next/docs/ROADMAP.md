## 0단계 결과 (완료)
- Next.js 16 + TypeScript, Drizzle ORM. DB는 `DATABASE_URL`이 있으면 Postgres, 없으면 내장 PGlite(Docker 불필요).
- 도메인 규칙 (`src/lib/core`): 개설 검증(정가·원가·마감·출고일), 마감 판정(실제 마감 후에만), 연장 1회·사유 필수,
  1인 한도, 확정 수량=결제 완료분, 광고 문자((광고)·수신거부·21~08시 차단·수신동의만), 요금제·성공 수수료.
- 카페24 연동 (`src/lib/cafe24`): 앱 실행 HMAC 검증, OAuth 동의·토큰 교환·자동 갱신(암호화 저장), 429 재시도,
  찜·장바구니·수신동의·쿠폰·SMS·스크립트태그·주문 API 래퍼, 로컬용 가짜 쇼핑몰.
- 라우트: `/api/cafe24/launch`(앱 실행), `/api/cafe24/callback`(OAuth), `/api/cafe24/webhooks`(중복 제거 저장), `/api/health`.
- 테스트 30개 통과 (`pnpm test`).

## 2단계 결과 (완료)
- 수집: 상품 목록을 훑어 상품별 찜·장바구니 수를 저장 (`collection_runs`, `demand_snapshots`). 진행 중이면 중복 수집 안 함, 실패하면 이전 완료 결과 유지.
- 레이더 화면 `/radar`: 첫 수집 중 진행률(S-E2) → 합계/찜/장바구니 정렬 목록. 찜·장바구니 0인 상품은 숨김.
- 도달 가능 인원: 상품을 눌렀을 때만 찜∪장바구니 회원 → 수신동의 대조, 숫자만 반환·회원 ID 미저장, 조회 기록은 감사 로그에.
  찜 100명 초과면 "일부만 확인" 안내 (PoC P8 결과에 따라 회원별 찜 경로로 보완).
- API: `GET /api/v1/demand`, `POST /api/v1/demand/collect`, `GET /api/v1/demand/reach`
- 임시 사항: 수집은 요청 뒤 백그라운드(`after`)로 돈다 → 5단계에서 큐 워커 + 매일 새벽 배치로 옮긴다.

## 1단계에서 확정할 것 (테스트몰 PoC)
코드에 `⚠ PoC 체크`로 표시해 둔 가정들:
1. 앱 실행 HMAC 서명 대상 문자열과 timestamp 단위 → `src/lib/cafe24/hmac.ts`
2. 웹훅 진위 검증 방식·trace id 헤더 → `src/app/api/cafe24/webhooks/route.ts`
3. API 요청·응답 필드명 (쿠폰 생성, SMS, 스크립트태그, 주문 쿠폰) → `src/lib/cafe24/api.ts`, 응답 샘플을 `tests/fixtures/`에 저장
4. P8 찜 100명 초과 수집 · P3 쿠폰 1,000명 발급 · P9 개인정보 설정 · P10 첫 수집 시간
5. P7 심사 전 지정 몰 설치 가능 여부
